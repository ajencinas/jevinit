# ZeroOps for IT operations: routine incident decisions, and where a model like Jev could help

ZeroOps is the aim of running routine incidents with no manual work: detected, triaged and resolved automatically, with people kept for the novel and the risky. AI agents for incident response became a real category in 2026 — every major platform ships one — yet in most estates the tools detect, correlate, execute and keep the record well (Datadog or Dynatrace, F5 telemetry and network monitoring, ServiceNow, PagerDuty, Rundeck or Ansible) while the judgment calls in between still fall to hand-written rules or the on-call engineer: is it real, whose is it, how bad, act or page. Those calls set MTTR and on-call load.

This repo looks at what a typed decision model, TypeSafe's Jev, can do in those calls from inside the existing tools. Each incident goes to the model once with a fixed set of typed questions: failure category, likely root cause, severity, proposed first action, whether a rollback looks safe, whether a person should be paged, and a few more. The model returns a choice or a score for each, with a probability. `zeroops/policy.py` compares those with thresholds and returns AUTO (act without a person), ESCALATE (page a person) or OBSERVE (log only), with the reason and the margin on every check. Nothing is executed; AUTO means the gate would have allowed the action.

We built a working demo to make this concrete: synthetic incidents, four models on the same harness, a Threshold Lab, a discussion deck and a demo video. The hub page, `outputs/index.html`, links them all. The encouraging results are speed, cost and a gate whose every decision can be explained (see Results). The incidents are synthetic and easy, so they show the mechanism and what the opportunity could look like; a company's own tickets are the real test.

The story ends with the value this could have (routing, triage, reversible fixes, economics), the open questions that decide whether the opportunity holds for a given estate (`outputs/3_open-questions-and-next-steps.md`), and a staged path to answer them on the reader's own data: a short diagnostic, an offline replay of closed tickets, then shadow and assist mode, with a decision point after each stage. The deck also says where outside help fits. The material is written to inform that decision. It quotes no prices, and because the harness runs any model, the choice of tool stays open.

Numbers are labelled *Our measurement*, *Vendor claim* or *Independent*.

**Start here:** every finished document is in **`outputs/`** (open `outputs/index.html`). The deck, PDF, demo video, results report and the interactive pages are all listed there, in reading order.

## How to run

Everything can be rebuilt from the saved decision logs in `work/results/`, with no API calls and no GPU:

```bash
./jev/bin/python -m pytest tests -q
./jev/bin/python scripts/run_all.py --skip-api --skip-local   # report, v4 deck, questions, lab, dashboard, two-outputs page, hub
./jev/bin/python scripts/demo_cli.py --incident INC-0001       # one saved decision in the terminal
```

`run_all.py` runs, in order: `run_eval.py` on the API backends, the local backends (Laya, then Kev), `report.py`, `build_v4.py`, `build_questions.py`, `build_lab.py`, `build_demo.py`, `build_race.py`, then `build_hub.py`. Its flags:

| Flag | Effect | Cost |
|---|---|---|
| `--skip-api` | don't re-run the two Jev endpoints; use the saved logs | |
| `--skip-local` | don't re-run Laya and Kev; use the saved logs | |
| `--start-kev` | start the Kev server if it isn't up, and stop it again when the Kev run ends | GPU |
| `--skip-demo` | don't rebuild the dashboard | |
| `--race-live` | re-record the two-outputs page (`outputs/one-incident/`) with one call each to Jev and a chat model | paid, a fraction of a cent |
| `--videos` | regenerate the demo voice-over and render the demo video | paid (ElevenLabs, TTS), several minutes |
| `--dry-run` | print the steps without running them | |

Without any flag it re-runs both Jev endpoints over the corpus (paid, cents at list price) and Laya, plus Kev if its server is already up. If no API key is set, the API step is skipped with a warning and the rest still runs. `report.py` refuses decision logs scored against a different corpus version, so a backend you didn't re-run after changing `zeroops/corpus.py` drops out of the report until you do.

Paid scripts, run on their own (keys in `.env`, see `.env.example`):

```bash
./jev/bin/python scripts/smoke_api.py                 # one call to each Jev endpoint
./jev/bin/python scripts/run_eval.py --backends api   # all incidents on both Jev endpoints
./jev/bin/python scripts/build_race.py --live         # replaces work/results/race_trace.json
```

## Maintaining this repo

These rules apply to people and to coding agents alike.

1. `work/results/facts.json` and `work/results/metrics.json` are the only source of numbers. `scripts/report.py` is the only script that writes them (and `outputs/7_results-report.md`, `demo_data.json`), in one pass over the decision logs. Builders read them at build time. Don't type a result into copy; for voice-over, convert numbers to words in code so a re-run updates the script. If a builder needs a number facts.json lacks, add it to `zeroops/facts.py`.
2. Every decision record carries the corpus fingerprint (`corpus_version`). Change `zeroops/corpus.py` and every backend has to be re-run; `report.py` skips stale logs rather than mixing versions (`--allow-stale` exists for inspection only).
3. Models are pinned in `zeroops/adapters.py` (`jev-1.13.0` native, `typesafe/jev-1.13-20260917` on OpenRouter). `TYPESAFE_MODEL` and `OPENROUTER_JEV_MODEL` override them. Don't measure on `jev-latest`, which moves with each release; the model each call resolved to is logged in the record.
4. The gate fails closed: a missing or malformed gating answer escalates, and a request to escalate or a high "page a human?" score wins over "not an incident". `policy.explain()` returns every check with its value, threshold, pass or fail, and signed margin. Show the margins whenever you show a decision.
5. `./jev/bin/python -m pytest tests -q` must pass before you change a claim. Add a test when you change the policy, the metrics or facts.
6. Don't hand-edit generated files; change the builder and re-run it. They are: everything in `work/results/` and `outputs/` (including `outputs/README.md`), the pages under `work/video/explainer`, `work/video/how-it-works` and `work/video/dashboard-loop`, and the Results block in this file. File locations live in `zeroops/paths.py`; change them there, not in a script. `run_all.py --skip-api --skip-local` re-runs all the offline builders.
7. Run `hyperframes check` before rendering a video (`run_all.py --videos` does). The hub marks any deliverable older than the newest decision log as possibly out of date.

## Writing rules

- Follow the arc, sector-neutral across IT operations (application incidents and network monitoring alike): the industry context, the gap in a modern estate, what a decision model adds (with the demo and its results as evidence), the value, and the path. Lead with what is promising and give the honest condition in the same sentence or paragraph; size caveats and put them where they matter (results and next steps).
- Next steps are a staged path with a decision point after each stage. Help offered by the presenting team stays concrete, modest and non-commercial: no prices, no engagement or partnership language.
- Give every figure its n and its label (*Our measurement*, *Vendor claim*, *Independent*). Show the exact-match action score whenever the lenient one appears, and say the lenient list was written after the first run.
- Put a caveat in the same sentence or paragraph as the claim it qualifies.
- Don't call the probabilities calibrated, the outputs deterministic, or the gate safe or proven; on this data none of that is shown (see the Results block). Let the mechanism, the numbers and the short path to a real test carry the interest, without adjectives.
- Don't use the phrases listed under `banned_phrases` in `inputs/claims.json`. `build_hub.py` fails if one reaches the hub page or the Results block.
- Plain sentences. Avoid the "X, not Y" construction, slogans, lists of three for their own sake, and closing lines that restate the headline.
- Use the same names everywhere: "Jev (TypeSafe API)", "Jev (via OpenRouter)", "Kev-4B (local GPU)", "Laya (local GPU)"; "exact action match" and "acceptable action".

## Known limitations

The figures behind these are in the Results block above and in `outputs/7_results-report.md`.

- **The corpus is small and easy.** The incidents are hand-written templates, each reused a few times with different service names and numbers, so the evidence is closer to the number of templates than to the number of incidents. Clues are explicit, which is why root cause scores near perfect. The same person wrote the incidents, the labels and the gate.
- **The lenient action score was written after the first run.** The acceptable-action list in `zeroops/schema.py` was added once the first results had been seen, and every alternative that changed Jev's score is the action Jev had picked. The exact-match score is the one to quote.
- **No held-out set.** The thresholds in `zeroops/policy.py` were set by hand before the first run and have never been tried on other incidents.
- **The gate is fragile.** Most automatic decisions passed the "page a human?" check just under its cut-off, and moving that one threshold changes the automation rate a lot. The Threshold Lab shows it.
- **Option order was never shuffled.** Jev proposed the first-listed action far more often than the labels call for it; the demo can't tell order bias from question design. Repeat calls weren't tested either.
- **The probabilities are not calibrated on this data, and the outputs are not deterministic.** High-confidence answers were right less often than their stated confidence, and the same model version on two endpoints gave different probabilities on every incident and flipped some gate outcomes. When it loads, the Laya checkpoint itself warns that its confidences should be treated as uncalibrated.
- **"No unsafe automation" rests on a handful of scenario types**, so its upper bound is wide. Laya's zero means nothing: it never acted.
- **Latency was measured once, from one workstation**, and the TypeSafe API returns no cost, so its cost is an estimate at OpenRouter's billed rate. Local models have no API fee; the GPU isn't costed. Kev ran untuned on a 16 GB card with CUDA graphs and the prefix cache off.
- **Jev is hosted, in early access, in one US region.** The model never executes anything; permissions, approvals, idempotency and rollback would stay with whatever executes actions.
- **The cascade the research describes** (rules first, then Jev, then an LLM when Jev is unsure) **is not implemented or measured here.**
